Q1: "Tell me about your ChillAdda project."
================================================================================

ANSWER:
"ChillAdda is a full-stack music streaming web application I built to provide 
a free alternative to paid services like Spotify. It's built with Next.js 14, 
MongoDB, and Redux Toolkit, and features user authentication, playlist 
management, favorites, song downloads, and real-time lyrics.

The app streams music from JioSaavn's catalog using their open-source API 
wrapper that I deployed on Vercel. Users can create accounts, build custom 
playlists, favorite songs, search across millions of tracks, and even download 
songs for offline listening.

I also made it a Progressive Web App, so users can install it on their phones 
and use it like a native application. The entire project is deployed on Vercel 
with MongoDB Atlas for the database."

KEY METRICS TO MENTION:
- Full-stack application (frontend + backend + database)
- 20+ features implemented
- JWT-based authentication with Google OAuth
- Redux state management with persistence
- PWA capabilities
- Fully responsive (mobile, tablet, desktop)


Q2: "Why did you choose Next.js over plain React?"
================================================================================

ANSWER:
"I chose Next.js over plain React for several important reasons:

1. **Built-in API Routes**: Next.js API routes eliminated the need for a 
   separate backend server. I could handle authentication, database operations, 
   and user management all within the same codebase.

2. **Server-Side Rendering**: For better SEO and initial load performance, 
   especially for pages like artist profiles and albums that benefit from 
   server-rendered content.

3. **File-based Routing**: The App Router makes navigation much simpler - 
   creating a new route is as easy as adding a folder. Plus, dynamic routes 
   like /artist/[id] are built-in.

4. **Performance Optimization**: Automatic code splitting, image optimization 
   with next/image, and built-in caching made the app significantly faster.

5. **Production Ready**: Next.js provides built-in optimizations, security 
   features, and deployment support that would take significant time to 
   configure in a plain React app.

The App Router in Next.js 14 also provides server components which help reduce 
the JavaScript bundle size sent to the client."


Q3: "Walk me through your authentication implementation."
================================================================================

ANSWER:
"I implemented a dual authentication system:

**Email/Password Authentication:**
1. During signup, I hash passwords using bcrypt with 10 salt rounds before 
   storing them in MongoDB. I never store plain-text passwords.

2. I generate JWT tokens with a 30-day expiry, signing them with a secret key 
   stored in environment variables.

3. For security, I store tokens in HTTP-only cookies rather than localStorage. 
   This prevents XSS attacks since JavaScript can't access HTTP-only cookies.

4. Every protected API route verifies the token by decoding it with the JWT 
   secret and extracting the user ID.

**Google OAuth:**
I integrated NextAuth.js for Google authentication, which handles the entire 
OAuth flow. When users sign in with Google, NextAuth creates or updates their 
user record and establishes a session.

**Password Reset:**
For password resets, I generate a unique token using the crypto module, store 
it in the user document with an expiration time, and send a reset link via 
Nodemailer. The token is single-use and expires after 1 hour.

All API routes are protected with middleware that verifies the JWT token before 
allowing access to user data."

**Why NOT Others:**

**Spotify API:**
- Requires OAuth with client ID and secret
- Cannot get streaming URLs without Premium account
- Strict rate limits (100 requests per day for free tier)
- Complex token refresh logic needed

**YouTube Music/API:**
- Requires Google API key with quotas
- Terms of Service are restrictive for music streaming
- Risk of account suspension
- No official music streaming API

**Apple Music API:**
- Requires paid Apple Developer account ($99/year)
- Complex token generation process
- Limited to Apple ecosystem

**SoundCloud API:**
- Requires application approval
- Smaller music catalog
- Commercial use restrictions

JioSaavn gave me the freedom to build a fully functional music streaming app 
without worrying about costs, complex authentication, or rate limits."

Q6: "Explain your database schema and why you structured it that way."
================================================================================

ANSWER:
"I designed a normalized database schema with three main collections:

**1. User Collection:**
Stores authentication and profile data:
- userName, email, password (hashed)
- imageUrl (profile picture)
- resetPasswordToken and expiry (for password resets)
- isVerified and verificationToken (for email verification)
- Reference to userData (one-to-one relationship)

**2. UserData Collection:**
Stores user-specific application data:
- favourites: Array of song objects
- songHistory: Recently played songs
- playlists: Array of Playlist ObjectIds
- language: Preferred languages

**3. Playlist Collection:**
Stores custom playlists:
- name: Playlist name
- songs: Array of song objects with full metadata
- user: Reference to User who created it

**Why This Structure:**

1. **Separation of Concerns**: I separated authentication data (User) from 
   application data (UserData) because they serve different purposes and may 
   have different access patterns.

2. **Scalability**: If favorites or playlists grow large, I can easily move 
   them to separate collections with references, without affecting the User 
   collection.

3. **Data Integrity**: Using ObjectId references ensures referential integrity 
   between users and their playlists.

4. **Flexibility**: Storing complete song objects in favorites and playlists 
   allows offline access and reduces API calls to JioSaavn.

5. **Performance**: Common queries like 'get user favorites' or 'get user 
   playlists' are optimized with this structure.

**Trade-offs:**
- I'm storing full song objects rather than just IDs, which increases storage 
  but significantly reduces API calls and improves performance.
- For a production system at scale, I might introduce a Songs collection and 
  use references, with caching layer for frequently accessed songs."


Q7: "How did you handle state management? Why Redux?"
================================================================================

ANSWER:
"I chose Redux Toolkit for state management, specifically for the music player 
functionality, because:

**Why Redux for This Project:**

1. **Global Player State**: The music player needs to be accessible from 
   anywhere in the app - homepage, search results, playlists, etc. Redux 
   provides a single source of truth.

2. **Complex State Logic**: The player has complex state:
   - Currently playing song
   - Queue of songs
   - Play/pause status
   - Current position in queue
   - Shuffle/repeat modes
   - Volume level
   
3. **State Persistence**: With redux-persist, I can save the player state to 
   localStorage, so when users return, their queue and position are maintained.

4. **Predictable Updates**: Redux's unidirectional data flow makes debugging 
   easier. I can see exactly how state changes over time.

**Implementation Details:**

I created three Redux slices:

1. **playerSlice**: Manages active song, queue, playback state
2. **loadingBarSlice**: Controls the top loading bar progress
3. **languagesSlice**: Stores user language preferences

**Why Not Context API:**
While Context API works for simpler state, Redux Toolkit provides:
- Better performance for frequent updates (player seeking, volume changes)
- DevTools for debugging
- Middleware for side effects
- Built-in persistence

**Redux Persist:**
I integrated redux-persist to save state to localStorage. The player state 
survives page refreshes, browser closes, and even crashes - providing a 
seamless user experience.

For server state (user data, playlists), I fetch directly from API routes and 
store only in local component state or Redux when needed globally."


Q8: "What was the most challenging part of this project?"
================================================================================

ANSWER:
"The most challenging aspect was handling CORS issues when fetching lyrics from 
third-party APIs. Here's how I solved it:

**The Problem:**
I wanted to display song lyrics, but most lyrics APIs were blocked by CORS 
policies when called from the browser. The browser would block requests to 
cross-origin resources without proper CORS headers.

**My Solution:**
I implemented a multi-layered approach:

1. **Proxy Server**: I used AllOrigins (https://api.allorigins.win) as a CORS 
   proxy. It fetches the data server-side where CORS doesn't apply, then 
   returns it to my app.

2. **Fallback Logic**: I integrated two lyrics sources:
   - Primary: Musixmatch API
   - Fallback: YouTube Lyrics API
   
   If Musixmatch fails or returns empty lyrics, it automatically tries YouTube.

3. **Validation**: I added validation to check if lyrics are actually valid 
   before displaying them, filtering out empty responses.

**Code Flow:**
```
Try Musixmatch → Validate → If valid, return
                          → If invalid, try YouTube
                          → Validate → If valid, return
                          → If both fail, show "Lyrics not available"
```

**Other Challenges:**

1. **JWT Security**: Initially stored tokens in localStorage, but learned about 
   XSS vulnerabilities and switched to HTTP-only cookies.

2. **Player State Persistence**: Lost state on refresh. Solved with 
   redux-persist.

3. **Music Streaming URLs**: Some URLs expired. Implemented re-fetching logic 
   when playback fails.

These challenges taught me about security best practices, error handling, and 
building resilient applications."

Q14: "Can you explain the music player implementation?"
================================================================================

ANSWER:
"The music player is the core feature of the app. Here's how I built it:

**Architecture:**
1. **Redux Store**: Central state management
   - activeSong: Currently playing song data
   - currentSongs: Queue of songs
   - currentIndex: Position in queue
   - isPlaying: Play/pause state
   - isActive: Player active/inactive

2. **MusicPlayer Component**: Main player UI
   - Controls (play, pause, next, previous)
   - Seekbar (progress and seeking)
   - Volume control
   - Song info display

3. **HTML5 Audio Element**:
   ```jsx
   <audio
     ref={audioRef}
     src={activeSong?.downloadUrl[0]?.url}
     onEnded={handleNextSong}
     onTimeUpdate={updateProgress}
   />
   ```

**Key Features:**

1. **Play/Pause**:
   - Redux action updates isPlaying state
   - Component uses audioRef.current.play()/pause()

2. **Next/Previous**:
   - Update currentIndex in Redux
   - Load new song from currentSongs array
   - Start playing automatically

3. **Seekbar**:
   - Display: (currentTime / duration) * 100
   - Seek: audioElement.currentTime = newPosition
   - Real-time updates via onTimeUpdate event

4. **Shuffle**:
   - Randomize currentSongs array
   - Reset currentIndex to 0
   - Fisher-Yates shuffle algorithm

5. **Repeat Modes**:
   - Off: Stop after queue ends
   - One: Loop single song (onEnded → replay)
   - All: Loop entire queue

6. **Volume Control**:
   - audioElement.volume = value (0.0 to 1.0)
   - Persist volume to localStorage

7. **Queue Management**:
   - Add/remove songs from queue
   - Drag-to-reorder (future feature)

**State Persistence:**
When page refreshes:
1. Redux Persist loads state from localStorage
2. Player restores:
   - Last played song
   - Queue position
   - Volume level
   - Play/pause state (paused on reload)

**Performance Optimizations:**
- Debounce seek updates
- Lazy load album art
- Preload next song in queue
- Clean up audio element on unmount

**Challenge Solved:**
Streaming URLs sometimes expire. Solution:
- Catch playback errors
- Re-fetch song data
- Update URL and retry
- Display error if fails

This architecture provides a smooth, app-like music experience."
